## 1. What Exists Today

### 1.1 Migration Numbering & Application

- **Tool:** `golang-migrate/v4` wrapped by `cmd/migrate/main.go`.
- **Numbering:** 4-digit zero-padded sequential prefix: `0001_`, `0002_`, etc.
  `runCreate()` scans the `migrations/` directory, finds the highest existing prefix, and increments.
- **File pairs:** `NNNN_name.up.sql` / `NNNN_name.down.sql`.
- **Application:** `make migrate-up` → `go run ./cmd/migrate up`. Reads `DATABASE_URL` env or falls back to `postgres://ser:ser@localhost:5432/ser?sslmode=disable`.
- **Rollback:** `make migrate-down` → `go run ./cmd/migrate down 1` (steps -N).
- **Create:** `make migrate-create NAME=foo` → auto-generates next numbered pair.
- **Current migrations:**
  - `0001_init_users_sessions` — `users`, `sessions`, `idempotency_keys` tables.
  - `0002_rooms_versions` — `rooms`, `room_versions` tables.

### 1.2 Repo Layer Pattern

- **DBTX interface** (`internal/platform/db/db.go`): abstracts `*pgxpool.Pool` and `pgx.Tx`.
  Exposes `Exec`, `Query`, `QueryRow` — the pgx subset needed by repos.
- **Concrete repos** accept `db.DBTX` in constructor (e.g., `NewPostgresRoomRepo(d db.DBTX)`).
  This allows injecting either a pool (production) or a transaction (tests).
- **Interface defined in each repo package**, not centrally. E.g., `catalog/repo.RoomRepo`,
  `auth/repo.UserRepo`. The service layer also re-declares the interfaces it consumes
  (e.g., `auth/service.UserRepo`).
- **Return types are always `pkg/models` types.** No pgx types leak into interfaces.
- **Pattern for queries:** Raw SQL strings (not an ORM). `pgx.Rows` scanning via helper functions
  (e.g., `scanRoomWithVersion`). Dynamic WHERE clauses built with `fmt.Sprintf("$%d", argN)`.

### 1.3 gqlgen Resolver Wiring

- **Config:** `gqlgen.yml` at repo root.
  - Schema: `internal/graphql/schema.graphql`
  - Generated code: `internal/graphql/generated/` (exec + models)
  - Resolvers: `internal/graphql/resolvers/` (layout: `follow-schema`)
- **Resolver struct** (`resolvers/resolver.go`): holds dependencies. Currently only `CatalogRepo catalogrepo.RoomRepo`.
- **Schema resolvers** (`resolvers/schema.resolvers.go`): auto-regenerated by gqlgen.
  Thin: extract args → call repo → map to generated model types.
- **Wiring in main.go:**
  ```go
  resolver := &resolvers.Resolver{CatalogRepo: roomRepo}
  gqlSrv := handler.NewDefaultServer(generated.NewExecutableSchema(generated.Config{Resolvers: resolver}))
  ```
- **Schema is additive-only** (per `docs/AGENTS/graphql.md`). No removals or renames post-merge.
- **Schema regen workflow:** Edit `schema.graphql` → run `go run github.com/99designs/gqlgen generate`
  (or via Makefile if target exists — currently no `make gqlgen` target; this is a gap).

### 1.4 Auth Middleware & ADMIN Checks

- **SessionMiddleware** (`internal/auth/transport/middleware.go`):
  - Extracts session cookie → `authService.ValidateSession()` → puts `*models.User` in context.
  - **Non-blocking:** unauthenticated requests pass through (user just isn't in context).
- **RequireAuth** middleware: returns 401 if no user in context. Currently unused in main.go but available.
- **RequireAdmin** middleware: returns 401 if no user, 403 if `user.Role != "ADMIN"`. Already implemented and ready to use.
- **UserFromContext** helper: extracts `*models.User` from context. Uses unexported key type to prevent collisions.
- **RBAC model:** `users.role` column, CHECK constraint: `'USER'` or `'ADMIN'`. Set at DB level, defaults to `'USER'`.
- **To add ADMIN-gated mutations in GraphQL:** The middleware is HTTP-level, but the GraphQL endpoint
  is a single POST handler. Options:
  1. Check `user.Role` inside each resolver (call `UserFromContext`, check role, return GraphQL error).
  2. Use a gqlgen directive (e.g., `@hasRole(role: ADMIN)`) with a custom directive handler.
  3. Wrap the entire GraphQL handler with `RequireAdmin` (too coarse — blocks all queries).

  **Option 1 is the current pattern** — resolvers already call `UserFromContext`. Directive-based auth
  would be cleaner but requires gqlgen directive setup that doesn't exist yet.

### 1.5 Go Module Layout for cmd/roomctl

- **Already exists:** `cmd/roomctl/main.go` — stub that prints "roomctl starting..." and exits.
- **Build target exists:** `make build` compiles `./cmd/roomctl` → `bin/roomctl`.
- **Make targets exist:** `make roomctl-validate` and `make roomctl-build` call `go run ./cmd/roomctl`
  with `validate` / `build` subcommands and optional `--room $(ROOM)` or `--all` flags.
- **Module boundary** (from `ARCHITECTURE.md`): `roomctl → publish (validate/build logic), models`.
  This means roomctl can import from `internal/publish/` (to be created) and `pkg/models`.
- **No flag parsing library** in go.mod yet. The stub uses raw `os.Args`. The existing `cmd/migrate`
  also uses raw `os.Args`. No cobra/urfave-cli dependency — consistent to keep it that way
  unless subcommand complexity warrants it.

## 2. Key Constraints (from DECISIONS.md & ARCHITECTURE.md)

### 2.1 Content-Addressed Bundle Storage (ADR-005)

- Bundles are keyed by **SHA-256 hash** of their content.
- Object storage path: presumably `bundles/<sha256hex>` (not yet implemented).
- **Immutability:** once a bundle hash is recorded against a `room_version`, the content at that hash must never change.
- Current schema: `room_versions.bundle_hash TEXT` — nullable, noted as "nullable until M2".

### 2.2 Idempotency via clientRequestId (ADR-009)

- All player-facing mutations accept `clientRequestId` (UUID v4).
- **Idempotency table** already exists: `idempotency_keys` (migration 0001).
  - PK: `key` (TEXT), stores `user_id`, `response_fingerprint`, `response_body` (JSONB), `expires_at`.
  - Same key + same fingerprint → return stored response.
  - Same key + different fingerprint → CONFLICT error.
- **For publishing mutations:** `publishRoomVersion` must accept `clientRequestId`. Fingerprint could be
  derived from `(roomId, versionNumber, bundleHash)` or similar.

### 2.3 Immutable Room Versions (ADR-005)

- "Published room content is immutable. Any change requires a new `room_version` with new bundle hash(es)."
- Runs pin to `room_version_id`. Rollback = pointer switch, not content mutation.
- **DB enforcement:** `room_versions` rows should never be UPDATEd on content fields after insert.
  Status can change (`PUBLISHED` → `DEPRECATED` → `DISABLED`), but `bundle_hash` and `version_number` are frozen.

### 2.4 rooms.active_room_version_id (Activation Pointer)

- **Not yet in schema.** The current `rooms` table has no `active_room_version_id` column.
- The current catalog query uses `MAX(version_number) WHERE status = 'PUBLISHED'` as a de facto
  activation pointer. This works but has a subtle difference from an explicit pointer:
  - MAX(version_number) doesn't allow "rollback to v2 while v3 exists as PUBLISHED".
  - An explicit `active_room_version_id` FK on `rooms` would decouple "latest" from "active".
- **Migration needed:** `ALTER TABLE rooms ADD COLUMN active_room_version_id UUID REFERENCES room_versions(id)`.
  This is an M2 schema change.

## 3. Likely Footguns & Edge Cases

### 3.1 Deterministic Tar Creation

- Content-addressed bundles require **deterministic archive generation**: same input files → same SHA-256 every time.
- Standard `archive/tar` in Go does NOT produce deterministic output by default:
  - **File ordering:** `os.ReadDir` returns directory-sorted order (Go 1.16+, uses `sort.Strings`),
    which IS deterministic. But symlink resolution and cross-platform path separators can vary.
  - **Timestamps:** File `ModTime`, `AccessTime`, `ChangeTime` in tar headers change between builds.
    Must zero them out or set to a fixed epoch (e.g., `2026-01-01T00:00:00Z`).
  - **Owner/group:** UID/GID and Uname/Gname vary by build machine. Must normalize (e.g., 0/0, root/root).
  - **Permissions:** File mode bits can differ. Normalize to standard values (0644 files, 0755 dirs).
- **Compression:** If using gzip, must use `gzip.NewWriterLevel` with fixed level AND set `Header.ModTime` to zero
  (gzip includes a timestamp in the header by default).
- **Recommendation:** Create a `deterministicTar()` helper that:
  1. Walks the directory with sorted output.
  2. Zeros all timestamps, UIDs, GIDs.
  3. Normalizes permissions.
  4. Writes tar (then optionally gzip with fixed header).

### 3.2 S3/R2 Client Configuration for Local Dev

- **MinIO is already in docker-compose** (`infra/docker-compose.yaml`):
  - Port 9000 (S3 API), 9001 (console).
  - Credentials: `minioadmin` / `minioadmin`.
- **No S3 client in go.mod yet.** Will use `aws-sdk-go-v2` (decided, see §4.1).
  Works with MinIO via custom endpoint + path-style addressing.
- **Configuration pattern:** The project reads all config from env vars (see `LoadConfigFromEnv`).
  Need env vars like:
  - `S3_ENDPOINT` (MinIO: `http://localhost:9000`, prod: R2/S3 endpoint)
  - `S3_BUCKET` (e.g., `ser-bundles`)
  - `S3_ACCESS_KEY`, `S3_SECRET_KEY`
  - `S3_FORCE_PATH_STYLE=true` (needed for MinIO, not for real S3/R2)
- **Bucket creation:** MinIO doesn't auto-create buckets. Decision (§4.6): `BundleStore`
  constructor calls `CreateBucketIfNotExists` on startup — idempotent, no separate setup step.
- **R2 note:** Cloudflare R2 is S3-compatible. Same SDK, different endpoint. Config-only difference.

### 3.3 Migration Ordering: ALTER TABLE on rooms

- Migration 0002 created `rooms` and `room_versions`. Adding `active_room_version_id` requires a new migration (0003).
- **Circular FK risk:** `rooms.active_room_version_id → room_versions(id)` and `room_versions.room_id → rooms(id)`.
  This is a valid pattern (both are nullable or deferrable), but:
  - Insert order matters: room first, then version, then UPDATE room to set active pointer.
  - The FK on `active_room_version_id` should be nullable (rooms can exist without an active version).
- **AGENTS.md rule:** "Never modify a migration file that has already been applied. Create a new one."
  So this must be `0003_add_active_room_version.up.sql`.
- **Down migration:** Must `ALTER TABLE rooms DROP COLUMN active_room_version_id` — straightforward.

### 3.4 gqlgen Schema Regeneration Workflow

- **Current gap:** No `make gqlgen` or `make codegen` target for the backend.
  The frontend has `make ui-codegen` but the Go side relies on manual `go run github.com/99designs/gqlgen generate`.
- **Regeneration is destructive to resolvers:** gqlgen's `follow-schema` layout means
  `schema.resolvers.go` is regenerated. Custom code survives if it's between the "DO NOT EDIT" markers
  correctly, but:
  - Adding a new query/mutation type creates new resolver stubs.
  - Renaming or removing a field can orphan resolver code (moved to end of file as "unknown code").
- **Workflow:**
  1. Edit `internal/graphql/schema.graphql` (add mutation type, input types, etc.)
  2. Run `go run github.com/99designs/gqlgen generate` from repo root
  3. Implement the generated resolver stubs in `schema.resolvers.go`
  4. Run `make ui-codegen` to regenerate frontend types
- **Potential issue:** `gqlgen.yml` has no `autobind` configured. All model types are generated
  into `internal/graphql/generated/models_gen.go`. The resolvers manually map between
  generated types and `pkg/models` types. This is intentional (keeps gqlgen decoupled from domain models)
  but means every new type needs a mapping function.

## 4. Decisions (Resolved)

All open questions have been answered by the human lead. These are binding decisions.

### 4.1 S3 SDK: `aws-sdk-go-v2` (standard)

- Use `aws-sdk-go-v2` for all object storage calls. Works with MinIO (local), S3, and R2 (prod)
  via endpoint configuration.
- No `minio-go`. Standard SDK keeps the dependency surface familiar.

### 4.2 roomctl: Separate Binary, Hybrid Access Pattern

- **Separate binary** (keep existing `cmd/roomctl/main.go`).
- **Hybrid access:** `roomctl publish` talks to S3 **directly** for bundle upload, then calls the
  BFF's **GraphQL mutation** for metadata registration (`publishRoomVersion`).
- This means roomctl needs:
  - S3 config (endpoint, bucket, credentials) — for direct upload.
  - BFF GraphQL URL + admin API key — for the `publishRoomVersion` mutation.

### 4.3 Dummy Room: Engine A

- First dummy room is Engine A (simulator). Simpler — no sandbox/judge infra required.
- The publishing pipeline is engine-agnostic (both produce bundles), so Engine A validates
  the full flow without extra moving parts.

### 4.4 CLI Auth: Static Admin API Key

- BFF reads `ADMIN_API_KEY` from env (32+ char random string).
- roomctl sends it via `Authorization: Bearer <key>` header.
- BFF middleware (new link in the existing chain):
  1. Checks `Authorization: Bearer` header.
  2. Compares using `crypto/subtle.ConstantTimeCompare` (timing-safe).
  3. If match: injects synthetic `&models.User{Role: "ADMIN", ID: "system-roomctl"}` into context.
  4. Existing resolvers see an admin user and proceed normally.
- **Ships in PR5** alongside the ADMIN resolver check. Same middleware chain, new link.

### 4.5 `make gqlgen` Target

- Add in **PR5** (alongside schema changes for `publishRoomVersion` mutation).
- Target: `make gqlgen` → `go run github.com/99designs/gqlgen generate`.

### 4.6 Bucket Auto-Creation on Startup

- `BundleStore` constructor calls `CreateBucketIfNotExists` — idempotent.
- `docker-compose up && make run` just works, no separate `make dev-setup` needed.
- **Ships in PR4** (BundleStore implementation).

### 4.7 ADMIN-Gating: Resolver-Level Check (Option 1)

- Check `user.Role` inside each admin resolver. Call `UserFromContext`, verify `"ADMIN"`,
  return GraphQL error if not.
- Matches the existing pattern (resolvers already call `UserFromContext`).
- No gqlgen directive setup needed.
